# CO-002：多 Agent 并行不可用，改为串行执行

- 日期：2026-11-07
- 类型：执行方式偏差记录
- 需求条款：V11 第十一节要求多 Agent 协同
- 当前实际：多 Agent 并行不可用，M1 按串行执行
- 是否影响验收范围：不影响
- 是否影响工期：影响，按约 8 个标准工作日排期

## 1. 失败分类

### 任务单未进入有效子上下文

多次子 Agent 启动后返回：

```text
尚未看到具体任务内容。请直接说明要处理的事项。
请告诉我具体要做什么。
当前工作区是……请告诉我具体任务。
```

按判定标准，这属于“返回‘你要我做什么’”的任务单丢失，而不是模型或 API 报错。

实际启动参数中包含 `message` 任务正文，不是有意只传角色名；但任务正文没有在子上下文中形成有效执行任务，因此从交付角度仍按任务单丢失处理。

本轮不修复此问题，不再尝试并行。

### API 协议错误

一次子任务返回：

```json
{
  "error": {
    "message": "The `reasoning_text` in the thinking mode must be passed back to the API.",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_request_error"
  }
}
```

同一批次其余任务已被调度，且没有任何 `429`、rate-limit 或并发额度错误。因此：

- 有证据支持：子 Agent 运行时的 thinking/reasoning 状态回传或模型适配层存在协议问题；
- 没有证据支持：并发限流是原因；
- 无法仅凭该错误证明：子 Agent 一定使用了与主 Agent 完全不同的模型配置。更准确的结论是“子 Agent 运行时与模型 API 的 reasoning 状态处理不兼容，具体配置差异未确认”。

## 2. 并行能力边界

工具声明最多 4 个并发槽位，其中包括主 Agent，因此最多同时运行 3 个子 Agent。

前置条件：

1. 多 Agent 功能已启用；
2. 子 Agent 创建成功；
3. 任务正文实际进入子上下文；
4. 各 Agent 不写同一目录；
5. 调度端能正常接收子 Agent 结果。

能力限制：

- 子 Agent 使用隔离上下文，不能假定自动继承主 Agent 的全部对话；
- 所有 Agent 共享同一工作区；
- 工具没有提供文件锁、目录锁或写入冲突预防；
- Git 只能事后发现差异，不能阻止两个 Agent 同时覆盖同一文件；
- 因此即使并行恢复，也只允许按所有权目录并行，同一目录必须单写者串行。

## 3. 当前执行决定

- 不再尝试并行；
- M1 按 `docs/superpowers/plans/2026-11-07-m1-implementation.md` 的串行顺序执行；
- 各角色身份仍保留，用于职责边界与代码审查；
- 实际实现、集成、测试按单写者顺序推进；
- 此项登记为对 V11 多 Agent 协同要求的事实偏差，不默认视为通过。
