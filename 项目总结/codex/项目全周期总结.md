# 高二英语智能练习系统项目总结与复盘

日期：2026-11-09  
范围：从仓库初始化到当前 `20261109_500` 浏览器练习闭环  
事实来源：Git 历史、`CHANGELOG.md`、`docs/change-log/`、`docs/milestones/`、`contracts/`、`qa/evidence/`、当前运行 API

## 1. 执行摘要

这个项目从一份较完整的 V11 需求开始，经过需求收敛、契约冻结、半日浏览器闭环、错题与历史报告、题库生成管线、500 题题库导入以及多轮用户体验修订，已经形成一条可运行的完整链路：

```text
题库生成/导入
  -> Bank 审核与激活
  -> 学生按低覆盖文章组卷
  -> 浏览器逐题作答
  -> 服务端交卷与判分
  -> 报告与薄弱点分析
  -> 原题回顾/历史报告/错题重做
```

当前事实状态：

- 当前 active Bank：`20261109_500`
- 当前规模：72 篇 / 500 题
- 前端：React Native + Expo Web，端口 8081
- 后端：FastAPI，端口 8000
- 数据库：PostgreSQL，固定端口 15432、数据库名 `english_practice`
- 需求版本：`contracts/VERSION = V11.5`
- Git 历史：项目总结编写前 80 个提交，从 `0a45042` 开始
- 当前选题规则：每套 1 篇完形 + 1 篇语法填空 + 1 篇阅读/七选五；优先三篇覆盖次数总和更少的组合，并列时优先 3 个话题

这个项目最大的价值不只是得到一套可运行页面，而是沉淀了一套“强约束教育内容 + AI 生成 + 可复核工程闭环”的方法。

## 2. 项目目标与范围演进

### 2.1 原始目标

面向广东省高二学生的人教版（2019）英语智能练习系统，核心目标包括：

- 围绕必修 1–3、选择性必修 1–2 的 25 个教学单元组织学习内容。
- 用教材词汇、语法白名单和册次标签限制 AI 生成范围。
- 在 30 分钟内完成一套包含完形、语法填空、阅读或七选五的练习。
- 交卷前不泄露答案和解析。
- 交卷后给出分数、分题型正确率、薄弱知识点、逐题解析和历史记录。
- 题库之间严格隔离，切换题库不影响旧会话、历史报告和错题状态。
- 支持错题重做、历史报告打开/删除、题库导入/导出和数据清理。
- 生成内容不能只看“像不像题”，还要通过结构、词汇、答案唯一性、解析依据、册次和语法覆盖等门禁。

### 2.2 范围如何变化

| 阶段 | 关键变化 | 结果 |
|---|---|---|
| V11 初始 | 手机真机 + Expo + Docker + PostgreSQL + Redis + 完整多 Agent | 形成完整愿景，但首日工程成本过高 |
| CO-001 | 补入基础不定式 `infinitive_nonfinite` | 语法白名单从 14 行/20 项变为 15 行/21 项 |
| CO-002 | 学生端改为 Expo Web，真机验收后置 | 保留 RN 代码，浏览器成为一期验收载体 |
| CO-003 | 收敛为半日最小闭环 | 首页、练习、报告三页；30 题；PostgreSQL 持久化 |
| CO-004 | 语法填空改为语篇后四选一；报告与原题双向跳转 | 取消手输，提升可判分性和回顾体验 |
| CO-005 | 逐题导航、模型分析、历史报告 | 形成完整学生练习闭环 |
| CO-006 | 交卷/退出确认弹窗 | 避免误交卷、误退出和脏会话 |
| M2 / M2.5 | 300 题题库、错题本、覆盖统计、题库切换、导入导出 | 从 Demo 升级为可运营题库产品 |
| M2.6 | 72 篇/500 题生成标准、Stage A 生成、往返评审 | 形成 AI 题库生产与修订规范 |
| 2026-11-09 | 选题规则先简化、再改为低覆盖次数优先；主页与答题交互持续修订 | 从“规则堆叠”回到可解释的两条规则 |

### 2.3 需求澄清做得好的地方

- 用户持续追问具体数字，暴露了“20 个语法项目 / 25 单元”“60 题 / 11 篇”“1967 词 / 3000 词”等口径冲突。
- 把“已写入”与“已验证”分开，要求贴原文、行号、SQL、grep 和截图，避免只凭口头汇报签字。
- 对“多 Agent 并行不可用”保留偏差记录，没有把串行执行包装成并行完成。
- 对不同阶段的验收范围写了明确 tag，例如 `co003-halfday-closedloop`，避免把半日闭环误称为完整 M1。
- 允许“缩小当日范围”，但不允许降低答案安全、数据持久化、质量门禁等核心约束。

### 2.4 需求阶段暴露的问题

- 初始需求同时包含完整产品愿景和首日交付目标，导致工程、内容、模型和部署并行争夺关键路径。
- 部分口径依赖口头语境，例如“30 分钟卷”“1 篇阅读或七选五”“11 篇/60 题”，到实现阶段才被数字拆解发现冲突。
- 界面细节如按钮位置、间距、正文宽度、题型名称、报告布局在功能完成后多轮调整，说明早期缺少低保真交互稿。
- 历史文档与当前数据库状态一度不一致。README 和交接文档还记录 300/47 题库，而当前 active Bank 已是 500/72；应以实时 API/数据库和新的当前状态文档为准。

## 3. 技术主线与架构选型

### 3.1 最终技术主线

```text
Expo Web
  -> FastAPI / OpenAPI
  -> PostgreSQL
  -> 题库生成/审核脚本 + DeepSeek 或本地 Qwen
  -> qa/evidence 与自动化验收
```

核心选择：

- **React Native + Expo Web**：保留未来回手机端的可能，同时用浏览器快速验收。
- **FastAPI**：便于定义 Pydantic 请求、OpenAPI 契约和同步数据库访问。
- **PostgreSQL**：Bank、会话、题目快照、作答、报告、错题和审计需要关系约束与事务。
- **OpenAPI 生成 TypeScript 类型**：避免前端凭想象调用不存在的 API。
- **JSON Schema + 严格校验器**：AI 输出不能直接入库。
- **本地规则 + 远程 LLM**：结构化内容用确定性规则，语义质量用 Pro 模型或人工复核。
- **原生 PostgreSQL ZIP 落地**：在 Docker/WSL 环境受阻时，不伪装 Docker 验收，改用可验证的本机 PostgreSQL。

### 3.2 Bank 是核心边界

Bank 不只是“题库名称”，而是：

- 题目、语篇、生成批次、审核、Coverage 和历史记录的隔离边界。
- 新会话创建时快照 `bank_id`、名称和版本的来源。
- 错题、覆盖、报告和旧题回顾的归属范围。
- 部分唯一索引保证同一时刻最多一个 active Bank。

因此系统禁止跨 Bank 混抽，也不允许向旧 Bank 静默追加题目。换库只影响之后创建的新会话。

### 3.3 关键稳定性设计

- 服务端 deadline 是计时权威，不用浏览器本地时间。
- 交卷使用 `Idempotency-Key`，重复提交返回同一报告。
- 交卷前接口不返回答案、解析或正确项。
- 报告保存完整题目、选项、作答、正确答案、对错和解析快照。
- 删除报告使用软删；学习状态与错题记录按产品语义保留。
- 题库维护和切换接口只接受本机回环来源。
- PostgreSQL 启动门禁同时校验固定端口 15432、实际端口和数据库名 `english_practice`。
- 组卷日志记录当前 Bank 规模、覆盖次数、话题和题目覆盖信息，便于复核。

### 3.4 架构层面的不足

- 组卷规则曾经过度复杂：册次、难度、五档、grammar tag、知识点、错题池、并发语篇和最近三套权重同时参与。题库小时这些规则互相锁死，形成 `NO_VALID_PAPER_ASSEMBLY`。
- 复杂规则产生“为了通过门禁而回填语义字段”的风险，例如题级 `book_source` 被填成与篇级内容不一致的值。
- 测试环境中固定名称的 M2.5 测试 Bank 会残留，导致第二次全量执行出现唯一键冲突。应改为每测试唯一名称或事务回滚。
- 部分交接文档重复记录历史题库，缺少一个始终实时的“当前运行状态”单一入口。

## 4. 数据与提示工程

这是项目中最关键、也最容易表面通过的部分。

### 4.1 内容边界

- 25 个教学单元，5 册教材，每册 5 单元。
- 21 个 grammar ID；每个 ID 有允许册次集合和授权子项集合。
- 双标签题只允许最多两个 grammar ID，且 `book_tag` 必须属于标签允许册次的交集。
- 词汇白名单由三层构成：义务教育基础、必修新增、选必新增，并冻结词形归一规则。
- 当前白名单口径为 3021 个单词语元 + 392 个短语，共 3413 项。

### 4.2 生成管线

当前文本生成不是“一次让模型输出整库”，而是：

```text
计划/配额
  -> 单篇语篇
  -> 语篇结构校验
  -> 单题或分批题目
  -> 固定答案约束
  -> 干扰项生成
  -> 中文解析
  -> Schema / 词汇 / 泄漏 / placeholder / evidence 校验
  -> Pro 或人工语义复核
  -> 合并为 Bank
```

重要的提示工程做法：

- `json_object` / `json_schema` 强制结构。
- 一次只生成一篇，避免 72 篇整包输出截断。
- 固定正确答案和 question index，降低答案漂移。
- 解析单独请求，输入固定题干、选项和答案，禁止模型重写题目。
- 阅读题必须有正文逐字符存在的 `evidence_sentence`。
- 完形/语法答案及屈折形式不得在正文泄漏。
- 失败有有限修复轮次，不无限重试。
- 成本账本记录 prompt/completion token、请求 ID、finish reason 和人民币成本。
- 连续 5 次传输失败打开熔断；达到预算阈值停止。
- 原始响应和失败分类进入 `qa/evidence`，而不是只保留最终成功样本。

### 4.3 质量门禁分层

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| JSON/Schema | 字段完整、类型正确 | 内容是否可解 |
| 正则/词形/占位符 | 结构、泄漏、编号、选项形态 | 语义是否真正成立 |
| 数值审计 | 配额、分布、覆盖、重复度 | 题目是否值得学生做 |
| Pro/人工 | 唯一最佳答案、解释真实性、语篇连贯 | 仍不是绝对真理，需要抽检 |

这一分层非常重要。机器校验通过只能说“没有发现已知结构错误”，不能自动升级为“内容质量已验收”。

### 4.4 真实踩坑

- 答案出现在正文或空位处，导致直接泄题；后期将检查移到持久化前和渲染边界。
- 干扰项从“明显荒谬”改成近义项后产生双解，证明唯一最佳答案必须由上下文证据支撑。
- 解析引用正文中不存在的句子，说明解析必须逐句对正文复核。
- 篇级 `book_source` 和题级 `book_source` 被混用，出现一篇完形分属多个教材单元。
- 为了满足 grammar 册次交集而倒填 `book_source`，字段通过了、语义却被掏空。
- 软删与硬删混用造成不可恢复数据丢失，后续明确报告删除的产品语义。

### 4.5 对下一个 AI 项目的直接建议

1. 先定义机器契约，再写提示词；提示词是执行器，不是数据库 Schema。
2. 一次模型请求只生成一个可验证单元，合并由确定性脚本完成。
3. 所有模型自报字段都要重新计算或交叉核验。
4. 机器门禁、语义门禁、人工抽检必须分层汇报。
5. 记录失败样本和不合格原因，否则无法判断“失败率”与“质量趋势”。
6. 固定输入、分阶段生成、修复循环和成本账本，优先级高于换更大模型。
7. 不要让模型在正文、标签和解释三处同时自由发挥。

## 5. 工程落地、上线与稳定性

### 5.1 做得好的部分

- 先执行 `git init` 和基线提交，之后每个任务一次 commit。
- 用 `contracts/VERSION`、OpenAPI、Schema、runtime 和 design tokens 做单一事实源。
- 对版本不一致、端口错误、数据库名错误采用 fail-closed。
- 对浏览器页面做真实端到端验证，而不是只跑单测。
- 保留 `qa/evidence`：API 响应、数据库计数、截图、日志、原始模型响应和成本报告。
- 使用短周期范围收敛：先跑通三页闭环，再补错题、历史、导入导出和题库生成。
- 对用户立即反馈的问题快速小步修正：按钮可见性、自动跳题、报告返回、正文宽度、页面留白。

### 5.2 做得不好的部分

- 环境前置没有一次盘点完整，WSL、虚拟化、管理员权限和 PostgreSQL 安装消耗了关键路径时间。
- 一度把“数据库层未验证”的自测说成近似通过，后来才明确数据层实际状态。
- 复杂组卷规则没有先做可行性证明，导致规则“写在代码里”但没有可执行组合。
- 测试依赖固定数据库 Bank ID 和固定测试名称，回归不幂等。
- 前端曾按想象的 API 写调用，后来必须用 OpenAPI 客户端/契约对照消除漂移。
- UI 需求在开发后多轮修正，说明应有早期线框和交互验收清单。

### 5.3 运维与发布清单

- 启动前检查 Node 24、Python 3.12、PostgreSQL 15432。
- 确认 active Bank 与题量。
- 确认 `/healthz`、`/api/v1/healthz`、Expo Web 8081 均可访问。
- 交卷测试必须检查幂等、报告四要素和交卷前无答案。
- 每次契约修改后运行 OpenAPI 生成、M0 检查、API 对照和 TypeScript。
- 每次题库导入后检查命名唯一、active 状态、覆盖快照、题型/难度/册次、语义抽检。
- 发布后检查历史报告、错题状态、题库切换和报告删除是否仍属于正确 Bank。

## 6. AI 协作 Skills 使用图谱

这里的“Skill”指 Codex 可加载的专业工作流资产，不等同于普通脚本。

| Skill / 工作流 | 项目中解决什么问题 | 结果与评价 |
|---|---|---|
| `test-driven-development` | 选题规则、解析接口、UI 行为修改前先写失败测试 | 效果明显。尤其适合“看起来只是改字段”但实际有回归风险的任务 |
| `agent-browser` | 真实浏览器点击、表单、跳转、截图、滚动位置和元素可见性验证 | 成为 UI 验收主手段，比只看源码更可靠 |
| `skill-creator` | 把题库生成、评审、发布门禁沉淀为项目专用 Skill | 本次新增技术资产，后续可复制到其他教育内容项目 |
| `writing-plans` / `executing-plans` 对应的计划文档方法 | M0/M1 任务拆解、里程碑实施计划、阶段交付 | 对长任务有效，但计划必须随需求和当前数据库状态更新 |
| `subagent-driven-development` / 多 Agent 并行 | 原计划用于多个契约文件并行评审 | 本次失败，任务单未稳定进入子上下文，另有 reasoning API 错误；实际改为串行 |
| 浏览器验收脚本（Playwright 等仓库脚本） | 批量生成 M2/M2.5/M2.6 浏览器证据 | 是工程工具，不是 Codex Skill；适合固定回归，但需避免与真实页面状态脱节 |

Skill 使用上的经验：

- Skill 适合固化“决策顺序和门禁”，不适合替代当前项目事实。
- 每次使用前都应读取最新 Skill 和项目契约。
- 对 UI 任务，Skill 的浏览器验证应包含元素可见性、跳转、坐标和数据状态，不只截一张图。
- 对内容生成，Skill 必须规定“何时读 Schema、何时拒绝、何时请求人工复核”。
- 多 Agent 只有在任务单、所有权目录和合并机制都可靠时才适合并行；本项目证明共享工作区默认串行更稳。

## 7. 综合评价

### 7.1 做得好的

- 敢于在数字矛盾出现时停下来，而不是静默生成。
- 把答案安全、Bank 隔离、服务端计时、幂等和报告快照当成不可退让的底线。
- 从“规则越多越智能”转向“少而可解释、可验证”的组卷策略。
- AI 内容处理从提示词工程升级为 Schema、校验器、Pro/人工、成本账本的组合工程。
- 保留完整证据链，具备追溯能力。

### 7.2 做得不好的

- 早期计划过大，导致环境、前端、后端、AI 生成和内容质量同时争抢时间。
- 复杂组卷规则对题库规模假设不足，出现规则互相锁死。
- 语义标签与教材出处曾被当作“可通过校验的字段”，而不是内容事实。
- 文档状态多次滞后于数据库和实现。
- 自动化测试对共享数据库状态考虑不足。
- UI 评审偏晚，仍有较多“做成后再调”的返工。

## 8. 下一个项目的最小行动清单

1. 第一天产出页面线框、数据流、运行环境和验收样例。
2. 先建立 Git、版本单一来源、OpenAPI 和错误码，再写业务。
3. AI 内容只生成单个可验证单元；禁止整库一次输出。
4. 任何模型自报数值都从源文本重算。
5. 机器门禁、Pro 门禁、人工抽检分别报告，不合并成一个“通过”。
6. 题库先证明“能组卷”，再追求复杂权重和分布。
7. 测试数据库使用唯一名称或事务回滚，保证重复运行。
8. 所有共享 UI 尺寸、颜色、字号来自 tokens。
9. 每个里程碑只签明确范围，欠账进入清单，不使用模糊的“基本完成”。
10. 每次交付附可复现命令、原始输出和截图；源码存在不等于功能通过。
